# Silent Payments test vectors

Four files, all published by the BIPs themselves, so a mistake shared with any one
implementation still shows up.

## `bip374_generate_proof_vectors.csv`, `bip374_verify_proof_vectors.csv`

`bip-0374/test_vectors_generate_proof.csv` and
`bip-0374/test_vectors_verify_proof.csv` from bitcoin/bips, with only their line
endings changed from CRLF to LF: 11 proof
generation cases (8 successes and 3 failures) and 17 verification cases (8 that
hold and 9 that must not).

Each row carries its own generator point, which is why
`silent_payments.dleq_prove` and `dleq_verify` take one; every device path uses
secp256k1's own G.

## `bip352_sending_vectors.json`

The **sending** half of `bip-0352/send_and_receive_test_vectors.json`, each case
kept verbatim under its own comment. The receiving half is what
`BIP352_RECEIVING` in `tests/test_silent_payments.py` already covers, and dropping
it here keeps a 412 KB file down to 73 KB.

A case's `expected.outputs` is a list of complete output sets, not one set: BIP-352
lets a sender order the recipients sharing a scan key as it likes, so the computed
set must equal exactly one of them. BIP-375 is what narrows the choice.

## `bip375_psbt_vectors.json`

`bip-0375/bip375_test_vectors.json` from bitcoin/bips, byte for byte: 20 valid and
22 invalid PSBTs, generated by <https://github.com/macgyver13/bip375-test-generator/>.

Three things about this file are worth knowing before reading the tests:

* Its P2WPKH and P2SH prevouts do not hash to the public keys the same inputs
  declare (`hash160(02c817bb...)` is `1e2ad787...`, the prevout is
  `0014229a72d3...`), so the vectors cannot be signed by anyone, and this device
  refuses them all. What they are used for is the derivation: the scripts they
  carry must be the ones this helper computes from their own shares and codes.
* One case, `input eligibility: bare OP_2 script...`, has a single input whose
  prevout is a bare `OP_2` script. That is not one of BIP-352's four eligible
  types, so there is no input sum to derive anything from, and the test skips it
  with that reason. The other cases all reproduce once eligibility is applied
  properly: BIP-352 skips a Taproot input whose internal key is the NUMS point H,
  and a P2SH input counts only when it wraps P2WPKH, so neither those inputs nor
  their ECDH shares belong in the sum. The NUMS case is the internal key in a
  control block; the vector that exercises it states no control block and puts H
  in the output key instead, which the test names as this file's shorthand rather
  than treating it as the rule.
* The case with two codes sharing a scan key assigns `k` by output index, while
  BIP-375's text sorts the codes to fix `k`, and the two give different scripts.
  This device follows the text, as Sparrow does -- drongo's `SilentPaymentUtils`
  sorts each scan key's group by the serialized code -- so its answer for that
  vector is the other one. The test records both, and will fail if either side
  changes.
